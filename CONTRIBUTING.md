# Contributing to Symptom Story

Thank you for helping make Symptom Story calmer, safer, and more accessible. This is a health-adjacent project, so small, well-explained changes are preferred over broad rewrites.

## Before you contribute

- Read the [product boundaries](README.md#why-symptom-story), [security policy](SECURITY.md), and [privacy and safety review](PRIVACY_AND_SAFETY_REVIEW.md).
- Search existing issues and pull requests before opening a new one.
- Use fictional information only. Never include your own or another person's symptoms, diagnosis, medication, journal content, contact information, or account data.
- Do not add analytics, advertising, AI/LLM processing, a paid service, a new permission, or a new health claim without prior maintainer approval.
- Never commit a `.env` file or credential. The Supabase service-role key must not appear in the client.

## Good first contributions

- Documentation clarity and typo fixes
- Accessibility improvements with a reproducible barrier description
- Tests for existing behavior
- Small UI refinements that preserve one-handed use
- Inclusive-language improvements
- Security hardening accompanied by a regression test

## Development setup

1. Fork and clone the repository.
2. Create a focused branch: `git switch -c fix/short-description`.
3. Install dependencies with `npm install`.
4. Copy `.env.example` to `.env` and use a non-production Supabase project.
5. Apply migrations in filename order.
6. Make the smallest change that solves the problem.

See the [README installation guide](README.md#getting-started) for complete commands.

## Required checks

Run before requesting review:

```bash
npm run lint
npm run typecheck
npm test
npm run test:coverage
npm run build:web
```

For visible changes, test approximately 375×667, 390×844, and 430×932, plus dynamic text and a screen reader when relevant. Include screenshots made with fictional data and describe the keyboard, reduced-motion, empty, loading, success, and error states you checked.

## Pull request checklist

- [ ] The change is focused and the motivation is clear.
- [ ] Tests cover changed behavior and all checks pass.
- [ ] No secret, real health information, or production identifier is present.
- [ ] Database changes include a forward-only migration and RLS review.
- [ ] New controls have labels, roles, states, focus behavior, and adequate touch targets.
- [ ] Charts or visual patterns include a plain-language alternative.
- [ ] Copy avoids diagnosis, causation, treatment-effectiveness, recovery, or guilt claims.
- [ ] Documentation and `.env.example` are updated when configuration changes.
- [ ] The PR lists known limitations rather than hiding them.

## Database and security changes

Never weaken or disable RLS to make a feature work. New user-data tables must:

1. reference `auth.users(id)` with an intentional deletion strategy;
2. enable RLS before API access is granted;
3. use operation-specific policies scoped to `authenticated`;
4. enforce ownership with `auth.uid()` in `USING` and `WITH CHECK` as appropriate;
5. revoke anonymous access;
6. validate input at the database boundary;
7. include cross-account denial tests.

Report vulnerabilities privately according to [SECURITY.md](SECURITY.md). Do not demonstrate an exploit in a public issue.

## Content and medical boundaries

The app may summarize objective entries (for example, “You recorded fatigue on four days”). It must not infer a diagnosis, recommend or stop treatment, predict recovery, or claim that a medication is working. Support and Safety responses must remain static, reviewed, and directed toward immediate human support—not generated by AI.

Use context-appropriate, inclusive language such as “people diagnosed with PMDD,” “postpartum people,” “feeding method,” and “support person.” Keep medically relevant terminology where clarity requires it.

## Commit style

Use an imperative, concise subject that describes the outcome:

```text
Add text alternative for mood trend chart
Harden journal ownership policy
Clarify local Supabase setup
```

## Review process

Maintainers may request product, accessibility, privacy, security, clinical, or legal review before merging. Submitting a contribution does not guarantee acceptance. All contributors must follow the [Code of Conduct](CODE_OF_CONDUCT.md).
